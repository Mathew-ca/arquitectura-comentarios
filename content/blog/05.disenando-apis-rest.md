Una API REST organiza el sistema alrededor de recursos, es decir, cosas con identidad como libros, usuarios o pedidos. Cada recurso tiene una dirección estable, por ejemplo `/libros/42`, y se manipula mediante los verbos de HTTP: GET para consultar, POST para crear, PUT o PATCH para modificar y DELETE para eliminar.

Los nombres importan más de lo que parece. Es preferible usar sustantivos en plural y evitar verbos en la ruta: `POST /pedidos` es mejor que `POST /crearPedido`. Una API con nombres consistentes se puede adivinar; quien conoce cómo se consultan los libros ya intuye cómo se consultan los autores.

Los códigos de estado son parte del contrato. Un 201 indica que algo se creó, un 400 señala que la petición está mal formada, un 404 que el recurso no existe y un 409 que hay un conflicto con el estado actual. Devolver siempre 200 con un mensaje de error en el cuerpo obliga a todos los clientes a inventar su propia lógica de interpretación.

Por último, hay que pensar en el cambio. Las APIs tienen clientes que no se actualizan al mismo ritmo que el servidor, así que conviene versionar desde el principio, ya sea con un prefijo como `/v1/` o con un encabezado. Agregar campos nuevos suele ser seguro; eliminarlos o cambiar su significado es lo que rompe a los clientes.
